# KisanSetu — AI-Based Crop Price Forecasting & Market Intelligence

Built for **Smart India Hackathon 2026 — SIH26132**
*"Strengthening Market Linkages and Price Discovery for Farmers"* (Government of Maharashtra)

KisanSetu predicts a pre-harvest **price range** (not a single false-precision number) for a
chosen crop, market, and week — with a confidence score, risk level, and plain-language
explanation of what's driving the price.

---

## What's actually in this project

This is a **real, database-backed, full-stack application** — not a mockup:

- **Database:** SQLite (default, zero config) via SQLAlchemy — swap to PostgreSQL by changing
  one environment variable. Tables: `crops`, `markets`, `price_records`, `weather_records`,
  `forecast_logs` (every forecast served is persisted).
- **ML pipeline:** feature engineering (lags, seasonality, rainfall deviation, market momentum)
  → a seasonal-naive baseline + XGBoost quantile-regression models (10th/90th percentile = the
  predicted range) → per-prediction explainability (XGBoost contribution values translated into
  plain-language sentences).
- **Backend:** FastAPI, serving both the JSON API and the frontend.
- **Frontend:** a single-page vanilla HTML/CSS/JS app (Chart.js vendored locally — no internet
  dependency at demo time) styled in KisanSetu's forest-green/gold identity.

**Important:** the seed data is realistic **synthetic** data (5 crops × 5 Maharashtra mandis,
3 years of weekly history) standing in for live AGMARKNET/e-NAM feeds, since live scraping needs
network/API access not guaranteed in every environment. The schema is designed so swapping in
real AGMARKNET/e-NAM ingestion later requires no changes downstream — see "Using real data" below.

## Folder structure

```
kisansetu/
├── backend/
│   ├── main.py              ← FastAPI app & all API routes (THE BACKEND ENTRY POINT)
│   ├── database.py          ← SQLAlchemy models (Crop, Market, PriceRecord, WeatherRecord, ForecastLog)
│   ├── schemas.py           ← Pydantic request/response schemas
│   └── services/
│       └── forecast.py      ← Loads trained models, builds features, computes each forecast
├── frontend/
│   ├── templates/
│   │   └── index.html       ← THE FRONTEND PAGE (single page app)
│   └── static/
│       ├── style.css        ← All styling
│       ├── script.js        ← All frontend logic (fetches from the API, renders chart/cards)
│       └── vendor/
│           └── chart.umd.js ← Chart.js, vendored locally
├── ml/
│   ├── features.py          ← Feature engineering, reads straight from the DB
│   ├── train.py             ← Trains baseline + XGBoost quantile models
│   ├── explain.py           ← Turns model output into plain-language drivers
│   └── artifacts/           ← Trained model files (.joblib) + metrics.json (generated by train.py)
├── data/
│   └── seed.py              ← Generates the synthetic dataset straight into the database
├── requirements.txt
└── kisansetu.db              ← SQLite database file (generated by seed.py)
```

**In short: the backend lives in `backend/`, the frontend lives in `frontend/`, both are served
by the same FastAPI process (`backend/main.py`) on port 8000.**

## Running it locally

```bash
# 1. Install dependencies
pip install -r requirements.txt

# 2. Seed the database (creates kisansetu.db with 3 years of synthetic mandi + weather data)
python data/seed.py

# 3. Train the forecasting models (creates ml/artifacts/*.joblib)
python ml/train.py

# 4. Start the server (serves both the API and the frontend)
uvicorn backend.main:app --reload --host 0.0.0.0 --port 8000
```

Then open **http://localhost:8000** in a browser. The interactive API docs are automatically
available at **http://localhost:8000/docs**.

## API reference

| Method | Endpoint | Description |
|---|---|---|
| GET | `/api/health` | Health check |
| GET | `/api/crops` | List all crops in the database |
| GET | `/api/markets?crop=Potato` | List markets that have data for a crop |

| POST | `/api/forecast` | Body: `{crop_id, market_id, target_date}` → predicted range, confidence, risk, drivers |

## Using real AGMARKNET / e-NAM data instead of synthetic data

Replace `data/seed.py` with a real ingestion script that writes into the same tables defined in
`backend/database.py` (`PriceRecord`, `WeatherRecord`). As long as the column names and types
match, **no other code needs to change** — `ml/features.py`, `ml/train.py`, and the API all read
from the database, not from any hardcoded file.

1. Pull historical + daily mandi price/arrivals data from AGMARKNET or e-NAM for your target
   crops/markets.
2. Pull matching daily/weekly rainfall & temperature data (e.g. IMD, Open-Meteo) for the same
   districts.
3. Write both into the database using the same schema.
4. Re-run `python ml/train.py` to retrain on real data.

## Deploying

This is a standard FastAPI app, so it deploys anywhere that runs Python. The app is
**self-healing on startup** — it automatically seeds the database and trains the model
the first time it boots if they're missing (see "Why self-healing?" below), so deployment
is simpler than a typical ML app.

### Render.com (recommended — free tier available)

1. Push this project to a GitHub repository.
2. On [render.com](https://render.com), click **New +** → **Web Service** and connect your repo.
3. Use these settings:

   | Field | Value |
   |---|---|
   | **Runtime** | `Python 3` |
   | **Build Command** | `pip install -r requirements.txt` |
   | **Start Command** | `uvicorn backend.main:app --host 0.0.0.0 --port $PORT` |
   | **Instance Type** | `Free` |

4. Click **Create Web Service** and wait for the build to finish.
5. On first request, the app will seed its database and train the model automatically
   (~30-60 seconds) — this only happens once per boot, not on every request.
6. Your app is now live at `https://<your-service-name>.onrender.com`.

**Note on Render's free tier:** it sleeps after 15 minutes of inactivity and wipes its
filesystem on every restart/redeploy. That's fine here — the self-healing startup logic
rebuilds everything automatically each time. The only downside is the first request after
a sleep takes ~30-60 seconds while it reseeds/retrains; every request after that is fast.

### Railway.app / Fly.io

Same idea — set the start command to
`uvicorn backend.main:app --host 0.0.0.0 --port $PORT` and let the self-healing startup
handle the rest. A `Procfile` and `.python-version` file are included in this repo for
platforms that read them automatically.

### Docker

A `Dockerfile` is included that pre-bakes the database and trained model at build time
(faster cold starts than relying on self-healing alone):
```bash
docker build -t kisansetu .
docker run -p 8000:8000 kisansetu
```

### Why self-healing?

Many free hosting tiers (including Render's free plan) use an **ephemeral filesystem** —
anything written to disk (like `kisansetu.db` or the trained `.joblib` model files) gets
wiped every time the service restarts or redeploys. Rather than relying on a fragile,
multi-step Build Command to regenerate these every time, `backend/main.py`'s startup
event checks whether the database is empty or the model files are missing, and
automatically re-seeds/retrains if so. This means the app **just works** on redeploy,
restart, or a fresh clone, regardless of which platform or build configuration you use.

## Retraining on a schedule

`ml/train.py` can be run any time new data lands in the database (e.g. via a daily cron job or
CI pipeline) — it always retrains from scratch using a time-ordered walk-forward split, so it
never leaks future prices into training.

---

## Model validation approach

- **Baseline:** seasonal-naive (same ISO week, averaged across prior years) — reported alongside
  every model run so it's clear whether the ML model is actually earning its keep.
- **Split:** time-ordered walk-forward (80/20), never a random shuffle, to avoid leaking future
  prices into training.
- **Metrics:** MAE, RMSE, MAPE, plus **range coverage** (how often the true price actually falls
  inside the predicted 10th–90th percentile range — the metric that matters most for a range-based
  forecast).
- All of these are surfaced live in the UI's "Model performance" panel and returned in every
  `/api/forecast` response, so judges can see real validation numbers, not just a demo output.

## Known limitations / next steps

- Seed data is synthetic — swap in real AGMARKNET/e-NAM data before any real-world use (see above).
- Only 5 crops × 5 Maharashtra markets are seeded; add more by extending `data/seed.py`'s
  `CROPS`/`MARKETS` lists (or, better, your real ingestion script).
- No authentication/user accounts — out of scope for the hackathon MVP.
- SMS/WhatsApp alerts, multi-language UI, and a native mobile app are natural next steps beyond
  this web MVP.
